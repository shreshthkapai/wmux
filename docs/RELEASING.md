# Releasing wmux

This runbook prepares and validates immutable GitHub releases. It does not
authorize rewriting the existing public repository history, changing GitHub
settings, pushing a tag, or publishing a release. Those actions require an
explicit maintainer decision.

## Release contract

- Initial release: `1.0.0`
- Initial tag: `v1.0.0`
- GitHub repository: `https://github.com/shreshthkapai/wmux`
- Release type: normal GitHub release, not a prerelease
- Release tool: dist 0.32.0
- Rust toolchain: 1.96.0
- Application binaries: `wmux` and `wmux-server`, always shipped together
- Installers: `wmux-installer.ps1` and `wmux-installer.sh`
- Updater: `wmux-update`
- Integrity: SHA-256 sidecars and GitHub artifact attestations
- Signing: unsigned; Authenticode and Apple notarization are not part of v1

## 1. Prepare the release commit

Work from `main`. Confirm that product changes are committed and that local
runtime files, credentials, build outputs, and agent files are not staged.

```powershell
git status --short --branch
git diff --check
```

Confirm the workspace version and changelog agree:

```powershell
rg -n 'version = "1.0.0"' wmux-clean/Cargo.toml
rg -n '^## \[1.0.0\]' CHANGELOG.md
```

For later releases, replace `1.0.0` throughout this runbook's commands with
the intended SemVer version. Add the release notes before changing the tag.

## 2. Run the local quality gate

From `wmux-clean/`:

```powershell
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --all-targets --locked
cargo check --locked --manifest-path fuzz/Cargo.toml --bins
cargo clippy --locked --manifest-path fuzz/Cargo.toml --bins -- -D warnings
cargo run --locked -p wmux-conformance --release
cargo run --locked -p wmux-stress --release -- --profile full
cargo run --locked -p wmux-bench --release -- --suite full --gate
```

Run native lifecycle tests on Windows, Linux, and macOS through the checked-in
CI workflow. A Windows cross-check of a macOS target is compile evidence only,
not native runtime evidence.

From the repository root, check the dependency and distribution policies:

```powershell
cargo deny --manifest-path wmux-clean/Cargo.toml check
dist generate --check
dist plan --tag=v1.0.0
```

The dist plan must list exactly one application, five platform targets, and
both binaries in every target archive.

## 3. Inspect a local Windows release build

```powershell
dist build --tag=v1.0.0 --target=x86_64-pc-windows-msvc
```

Locate the generated ZIP and its `.sha256` sidecar. Run the repository archive
verifier against an artifact directory containing all planned target archives:

```powershell
pwsh -NoProfile -File scripts/verify-release-archives.ps1 -ArtifactsDirectory artifacts
```

Extract the Windows ZIP and verify the paired versions:

```powershell
.\wmux.exe --version
.\wmux-server.exe --version
```

Both commands must print version `1.0.0`. Do not accept an archive containing
only the client; the client locates `wmux-server` beside its own executable.

## 4. Validate hosted CI

The release commit on `main` must have green results for:

- formatting, Clippy, workspace tests, and fuzz-harness compilation;
- portable semantic conformance on Windows, Linux, and macOS;
- native Windows, Linux, and macOS lifecycle tests;
- deterministic stress on all three OS families;
- the Windows release performance gate;
- dependency policy and dist plan checks.

Do not tag a commit while any required hosted job is pending or failing.

## 5. Decide the existing GitHub history cutover

The confirmed public GitHub repository contains an older C++ implementation,
while this Rust repository began with independent history. Before configuring
a remote or pushing, choose and document one of these approaches:

1. preserve the old default branch history through an explicit merge or an
   archive branch; or
2. replace the remote default branch after recording an immutable recovery
   reference to the previous tip.

Review the exact refs and recovery procedure before any destructive remote
operation. This runbook intentionally provides no force-push command. The
workspace rename from `wmux-clean/` is also a separate approved change; update
the single member path in `dist-workspace.toml` when that move occurs.

## 6. Configure repository release settings

Before the first public release:

- enable private vulnerability reporting;
- require the core and supply-chain workflows on `main`;
- grant GitHub Actions permission to create releases and attestations as
  generated by dist;
- confirm the default branch and repository URL;
- leave immutable releases disabled until every expected v1 asset has been
  published and validated.

No Windows or Apple developer certificate is required for an open-source
release. The README must continue to disclose platform trust prompts while the
binaries remain unsigned.

## 7. Tag and publish

Only after the history cutover is approved, the remote is configured, and the
release commit is present on `main`, create an annotated tag:

```powershell
git tag -a v1.0.0 -m "wmux v1.0.0"
git push origin v1.0.0
```

The generated release workflow builds all targets, creates checksums and
installers, emits attestations, and publishes a normal GitHub release only
after required build jobs succeed.

Never move a pushed release tag or replace a published immutable asset. Fixes
receive a new patch version such as `1.0.1`.

## 8. Validate published assets

Wait for both the generated release workflow and the `release-assets` workflow
to pass. The latter downloads all public artifacts, verifies their SHA-256
sidecars and contents, and executes both Linux x64 binaries with `--version`.

On clean Windows, Linux, and macOS hosts, run the public installer command from
the README. On each host verify:

```text
wmux --version
wmux-server --version
wmux new -s release-smoke
```

Detach, reattach, split both directions, change panes and windows, rename a
window, and finish the smoke session with `C-b X`. Verify `wmux ls` reports no
remaining smoke session.

Run `wmux-update` after a patch release is available and repeat the paired
version check. Before updating, finish active sessions and stop the server:

```text
wmux ls
wmux kill-server
wmux-update
```

## 9. Freeze and announce

After public installers, archives, checksums, attestations, and smoke tests all
pass:

1. enable GitHub immutable releases;
2. confirm `/releases/latest` resolves to the new normal release;
3. verify README installer URLs still resolve;
4. announce the release with links to the changelog and security policy.

If public validation fails, do not silently replace assets. Record the failure,
fix it on `main`, run the full gate, and publish a new patch version.
