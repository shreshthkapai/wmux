# Performance Baseline

`wmux-bench` is the repeatable performance baseline for terminal parsing,
rendering, resizing, IPC encoding, detached output catch-up, and multiple
clients. Its Codex and Claude workloads are deterministic VT-heavy generators,
not captured user sessions.

## Suites

The smoke suite is suitable for development and CI:

```powershell
cargo run -p wmux-bench -- --suite smoke
```

The full suite includes the 100,000-line history resize and sustained workloads:

```powershell
cargo run -p wmux-bench --release -- --suite full --json
```

Record debug and release separately. Never compare a debug wmux result with a
release tmux or zellij result:

```powershell
cargo run -p wmux-bench -- --suite full --json > wmux-debug-baseline.jsonl
cargo run -p wmux-bench --release -- --suite full --json > wmux-release-baseline.jsonl
```

The full debug suite is intentionally expensive. Use the smoke suite while
iterating and run both full profiles at performance milestones.

Run one workload or list all workload names:

```powershell
cargo run -p wmux-bench --release -- --list
cargo run -p wmux-bench --release -- --suite full --scenario frame-codex --json
```

## Metrics

Each JSON line reports elapsed time, input and operation throughput,
p50/p95/p99 operation or frame latency, allocation count, allocated bytes,
peak live bytes, emitted IPC bytes, maximum simulated queue depth, and
deterministic checksum.

`client_write_ns` measures time spent handing generated bytes to the benchmark
client sink. Physical terminal presentation time is terminal-specific and must
be measured separately in end-to-end profiling.

The allocation counter is process-global. Workload setup happens before the
measurement window so fixture construction does not contaminate hot-path
allocation measurements.

The authoritative grid uses compact copy-on-write lines and interned styles;
see `docs/compact-grid.md`. The history resize and split-storm workloads cover
the representation's main memory, snapshot, reflow, and scene-composition hot
paths.

profiling can inspect partial scenarios without triggering unrelated failures.

## Runtime Scheduling Baseline

The state-owner runtime has deterministic queue limits and service budgets:

| Control | Value |
| --- | --- |
| ConPTY read chunk | 16 KiB |
| Per-pane queued chunks | 64 |
| Per-pane turn | 64 KiB or 1 ms collection time |
| Output round | 4 ms |
| Control batch before output | 256 events |
| Client outbound queue | 4 MiB and 64 protocol messages |
| Maximum single client frame | 16 MiB plus frame header |
| Windows async runtime | 2 IOCP worker threads |
| Idle state-owner wake | next timer deadline or I/O event |

Tests in `wmux-server` verify lossless bounded overflow, adjacent chunk
coalescing, detached output processing, and round-robin progress under a noisy
pane. Performance changes to these values must run the smoke suite in both
debug and release plus an interactive multi-pane output test. Queue limits are
backpressure controls, not permission to discard PTY bytes.

Client render queues hold at most one in-flight render. Further damage is
coalesced in authoritative pane generations until the writer drains. IPC v3
moves variable payload allocations through decode and encode and writes frame
headers and payloads as separate vectors; see `client-backpressure-and-ipc.md`.

Windows client IPC, server accept/read/write, and ConPTY output are overlapped
operations driven by IOCP. The attached client no longer probes named pipes or
sleeps between input and output checks. The only periodic client timer is a
500 ms terminal-size verification fallback; native resize input still sends an
immediate resize event.

## Batched Parser Baseline

PTY chunks are parsed through the `vte` slice parser into semantic operation
batches. Printable text shares one batch arena, adjacent callbacks become one
`PrintRun`, and ASCII runs are written to grid line segments rather than
dispatched as individual byte operations. CSI parameters use the parser's
fixed 32-slot storage. See `terminal-batching-and-damage.md` for the generation
and journal contract.

The smoke replay fixtures are correctness-gated against the previous parser
after every frame. Performance comparisons must preserve those replay tests,
not merely improve throughput counters.

Representative Windows release results for the step 6/7 full suite on
2026-07-10 were:

| Scenario | Result |
| --- | --- |
| `parser-codex` | 168.7 MB/s |
| `parser-claude` | 170.2 MB/s |
| `frame-codex` p95 | 122.0 us |
| `frame-claude` p95 | 118.7 us |
| `detach-backlog` | 145.4 MB/s |

These are local reference values, not portable thresholds. Compare future
changes on the same machine and release profile.

## Hybrid Renderer Baseline

## Client Backpressure And IPC Baseline

The step 11/14 full release `large-paste` workload on 2026-07-11 encoded eight
8 MiB messages (64 MiB total) with one 64-byte bookkeeping allocation across
the measured loop. No payload-sized frame allocation occurred. IPC v3 emitted
67,108,936 bytes, exactly eight 9-byte headers plus the payloads.

The production transport consumes those same payload allocations into
vectored header/payload writes. Per-client byte accounting and redraw
coalescing are documented in `client-backpressure-and-ipc.md`.

## Resize Transaction Baseline

Step 12 computes each final window layout once and emits a coalesced pane-size
delta. Unchanged rectangles do no work; position-only changes do not reflow the
grid or resize the PTY; dimension changes resize exactly one authoritative
screen and at most one existing platform pane. Missing panes are spawned at
their final size. See `resize-transactions.md` for the complete contract.

The `split-storm` and `history-resize-100k` workloads remain the performance
checks for layout mutation and terminal reflow. Core and server tests include
an uneven three-pane resize where a one-column window growth must resize only
the pane that receives that column.

## Lazy Scrollback Reflow Baseline

Step 13 stores completed scrollback as immutable canonical logical lines and
keeps it out of width-resize work. Only the viewport, rows below it, and the one
unfinished logical line crossing the viewport boundary are reflowed. Historical
physical rows are materialized lazily and cached by width. See
`lazy-scrollback-reflow.md` for the representation and invalidation contract.

The full release workloads on the same machine on 2026-07-11 produced:

| Scenario | Result |
| --- | ---: |
| `history-resize-100k` p95 | 31.9 us |
| `history-resize-100k` allocations | 581 |
| `history-resize-100k` allocated bytes | 93.5 KB |
| `history-resize-100k` peak live | 14.3 KB |
| `parser-codex` throughput | 166.3 MB/s |

The recorded Step 8 resize baseline was 89.8 ms p95. Parser throughput remained
at its prior 167.0 MB/s baseline, showing that canonicalization did not move
cost into the output hot path.

## Post-Hardening Hot-Path Recovery

After the cancellable IPC-read fix and cursor transaction hardening, four
release runs were compared on the same Windows host before and after removing
redundant hot-path work. The parser now retains its text and semantic-operation
capacity between PTY chunks. The renderer writes numeric VT parameters directly
into its output buffer and shares authoritative full-width pane lines instead
of rebuilding them cell-by-cell. These changes preserve the damage journal,
client baselines, bounded queues, synchronized output, and dedicated IPC reader.

Median results across four full-suite runs were:

| Scenario | Before | After |
| --- | ---: | ---: |
| `parser-codex` throughput | 152.4 MiB/s | 159.6 MiB/s |
| `frame-codex` p95 | 70.8 us | 64.1 us |
| `frame-claude` p95 | 79.7 us | 54.8 us |
| `hybrid-frame-codex` p95 | 125.6 us | 55.2 us |
| `hybrid-frame-claude` p95 | 121.4 us | 58.6 us |
| `detach-backlog` throughput | 125.5 MiB/s | 153.7 MiB/s |
| `multiple-clients` p95 | 233.3 us | 154.7 us |

Measured allocation volume also fell from 20.46 MiB to 2.63 MiB for parser
replay, from 62.18 MiB to 44.15 MiB for Codex frame replay, and from 182.70 MiB
to 101.46 MiB for detached output. The history resize p95 previously fluctuated
from a 35.6 us median to 44.8 us; no resize code changed, and both remain far
below the 5 ms gate. The full release performance gate and all correctness and
conformance tests remain mandatory.

## Phase 5 Platform Dispatch Gate

The frozen `PtyBackend` seam is measured directly through a trait object. The
full workload submits 10,000,000 deterministic resize requests, checks every
submission through a rolling checksum, and measures allocations on the
workload thread so parallel test-harness activity cannot contaminate results.

The final Windows release run on 2026-08-21 completed in 68.906 ms at
145,124,611 operations/second with zero allocations, zero allocated bytes, and
zero semantic violations. The enforced floor is 20,000,000 operations/second.
This is adapter-dispatch evidence, not an end-to-end PTY throughput comparison;
the existing parser, render, backlog, queue, and latency gates remain required.
